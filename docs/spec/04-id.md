> 状态：**已实现**（10-05）——签名 + 实现 + 用例，wasm / js / wasm-gc 三档读数一致，native 档由 CI 出证。
> 实现在 `id/id.mbt`，公开接口在 `id/pkg.generated.mbti`，期望值在 `id/id_test.mbt` 与 `id/README.mbt.md`。
> 改任何期望串须单独一笔并给外部读数来源（门禁 G5）：实现落地前只动过两条**契约内部自相矛盾**的期望

## 0. 三条贯穿性规则

| # | 规则 | 为什么 |
|---|---|---|
| 0.1 | **时钟与熵都是参数**：`Snowflake::next(now_millis)`、`ObjectIdGen::next(timestamp_secs)`、`uuid_v4(rand)`、`nano_id(..., rand)` 全部显式注入；只有带 `_random` / `uuid_v4_random` / `nano_id_random` 后缀的入口才碰 `env.now()`/`env.rand()` | 零依赖契约只给两扇 OS 窗（`AGENTS.md`「零依赖四条」）。hutool 靠 `SystemClock`/`SecureRandom` 静态量，本库若照抄，这些格子就**永远不可测**（期望值会随机器漂）。注入版是纯函数 ⇒ 每条期望值都能钉死；便捷版是它的一层薄壳 |
| 0.2 | **不读 PID、不读网卡、不读 ClassLoader**：`machine`（ObjectId）与 `datacenter_id`/`worker_id`（Snowflake）一律由调用方给 | hutool 的机器码是 `NetworkInterface` 列表哈希 ‖ PID ‖ identityHashCode(ClassLoader)——三样全要 FFI。更糟的是它"取不到就随机"，等于静默降级成可能撞号的 ID。本库宁可**不给默认值**：谁生成 ID 谁负责节点编号（框架层从配置读），否则同机多进程撞号是迟早的事 |
| 0.3 | **不自旋、不 sleep**：同毫秒内 4096 个序列号用尽后，把逻辑时间戳推进 1 毫秒继续发号 | hutool 的 `tilNextMillis()` 是 `while (timestamp == last) timestamp = genTime()` 的忙等。本库的时钟是**传进来的**，对着注入值自旋既无意义也可能永不返回（注入的是纯数据，不是会走的钟）。推进逻辑时间戳保持"单调递增 + 同毫秒 4096 上限"这两条真语义，代价是发号速率超过 4096/ms 时时间戳会略微超前真实时间——这是可接受的，也是可测的 |

**这一批不含 UUID v5**：v5 的定义是 SHA-1(namespace + name)（RFC 4122 §4.3），而 SHA-1 在 `digest` 的下一批里（见 [`docs/ROADMAP.md`](https://github.com/mldong/moon-hutool/blob/master/docs/ROADMAP.md) 的「暂不做」）。hutool 本身也没有 v5——它的 `UUID.nameUUIDFromBytes` 是 JDK 那套**只吃 name、无 namespace**的 MD5 档，本库把它作为兼容档单列（#3.4），v3 则按 RFC 做完整的 namespace 版。

## 2. Snowflake（与 MyBatis-Plus 同 ID 空间）

位分配：**41 位时间戳 ‖ 5 位数据中心 ‖ 5 位 worker ‖ 12 位序列**，`TWEPOCH = 1288834974657`。
移位常数：`TIMESTAMP_LEFT_SHIFT=22`、`DATA_CENTER_ID_SHIFT=17`、`WORKER_ID_SHIFT=12`、`SEQUENCE_MASK=4095`。
血统：这套位分配是 Twitter snowflake 的公开规格，hutool `lang/Snowflake.java` 与 MyBatis-Plus `IdWorker` 都照它实现——**三者同号**，所以本库必须逐位一致，否则跨栈拿到的是不同 ID 空间。

## 3. UUID

| # | 签名 | 语义 | 边界/错误 | hutool 对位 | 差异声明 | 读数来源 |
|---|---|---|---|---|---|---|
| 3.1 | `uuid_nil : String` = `"00000000-0000-0000-0000-000000000000"` | nil UUID | — | `UUID.nullUUID()` | — | RFC 4122 §4.2 |
| 3.2 | `uuid_ns_dns` / `uuid_ns_url` / `uuid_ns_oid` / `uuid_ns_x500` : String | 四个预定义 namespace | — | 无（hutool 无 namespace 概念） | 本库按标准补，因为 v3 的定义就要 namespace | RFC 4122 §4.3：`6ba7b810-9dad-11d1-80b4-00c04fd430c8`（DNS）、`…811…`（URL）、`…812…`（OID）、`…814…`（X500） |
| 3.3 | `uuid_v3(ns : String, name : String) -> String raise IdError` | MD5(namespace 字节 ‖ name 的 UTF-8)，再置 version=3、variant=10xx | `namespace` 不是合法 36 位规范串 ⇒ `BadLength`/`BadHex` | hutool **无此件**（它的 v3 是 3.4 那档） | `name` 一律按 **UTF-8 字节**参与运算（与 `digest` 同口径）；输出小写带连字符 | 双实现互算：Python `uuid.uuid3` 与手算 `hashlib.md5(ns.bytes + name)` 逐条一致。例：`(dns, "www.example.com")` → `5df41881-3aed-3515-88a7-2f4a814cf09e`（原始 MD5 = `5df418813aed051548a72f4a814cf09e`，version/variant 位改动见下）；`(dns, "")` → `c87ee674-4ddc-3efe-a74e-dfe25da5d7b3`；`(url, "hutool")` → `6a2fefe3-8842-3671-9f35-f6e5a5ac58fb`；`(dns, "中文")` → `16f114b0-3b17-3212-8d00-64c5d765a004`；`(x500, "cn=hutool")` → `a79170fa-dbd9-3092-a405-b8adfccca9ae` |
| 3.4 | `name_uuid(name : String) -> String` | JDK `UUID.nameUUIDFromBytes` 兼容档：**只有 name、无 namespace** | 恒不失败 | `cn.hutool.core.lang.UUID.nameUUIDFromBytes` | 输入是字符串 ⇒ 固定按 UTF-8 编码（JDK 那侧由调用方给字节，同一字符串在 Java 里传 `getBytes()` 会随平台默认字符集变，本库不跟） | **本机 JDK 17 实跑**四条，与 `hashlib.md5` 推算逐条一致：`""` → `d41d8cd9-8f00-3204-a980-0998ecf8427e`（= MD5("") 改位）；`"abc"` → `90015098-3cd2-3fb0-9696-3f7d28e17f72`；`"www.example.com"` → `7c1767b3-0512-3600-bfd3-c2e618a86522`；`"中文"` → `a7bac223-9fcd-3b3a-8679-03d8077c4a07`（与 `digest` 已冻结的 `md5_hex("中文")` 同源，三方对齐） |
| 3.5 | `uuid_v4(rand : Bytes) -> String raise IdError` | 随机 UUID；`rand` 必须**恰好 16 字节**；置 `rand[6] = (rand[6] & 0x0f) \| 0x40`、`rand[8] = (rand[8] & 0x3f) \| 0x80` | 长度不是 16 ⇒ `EntropyTooShort(16, got)` | `UUID.randomUUID()`（那侧自己取熵） | 注入版是纯函数，所以能冻结期望值；便捷版见 3.6 | Python 同式现算：全 `0x00` → `00000000-0000-4000-8000-000000000000`；全 `0xFF` → `ffffffff-ffff-4fff-bfff-ffffffffffff`；`0..15` → `00010203-0405-4607-8809-0a0b0c0d0e0f`；`0x2A..0x39` → `2a2b2c2d-2e2f-4031-b233-343536373839` |
| 3.6 | `uuid_v4_random() -> String raise IdError` | `uuid_v4(env.rand(16))` | `env.rand` 给不出 ⇒ `NoEntropy`；**绝不静默回落固定种子** | `randomUUID(true)`（SecureRandom） | 单列这条的意义就是让"没有熵"变成一次可观察的失败而不是一个可预测的 UUID | 见 §6 熵档位实测 |
| 3.7 | `uuid_version(canonical : String) -> Int raise IdError` | 取第 15 个十六进制字符（version 高位段） | 长度/字符非法 ⇒ `BadLength`/`BadHex` | `UUID.version()` | 只读 version 段，不判 variant（variant 校验在 `valid` 包对位 `Validator.isUuid`） | 实测读数：`5df41881-3aed-3515-88a7-2f4a814cf09e`→3、`d41d8cd9-8f00-3204-a980-0998ecf8427e`→3、`00000000-0000-4000-8000-000000000000`→4、`2ed6657d-e927-568b-95e3-e5a295fed3ad`→5、`6ba7b810-9dad-11d1-80b4-00c04fd430c8`→1 |

**version/variant 位改写的定义**（3.3/3.4/3.5 共用）：16 字节大端序下，`byte[6] = (byte[6] & 0x0f) | (version << 4)`、`byte[8] = (byte[8] & 0x3f) | 0x80`。这条在 3.4 的交叉核对里被 JDK 读数验证过（`md5("abc")` 的 `4f` → `3f`、`d6` 保持 `d6`）。

**不做**：v1（要 MAC/node 与 clock sequence，全需 FFI）、v2（DCE 安全）、v6/v7/v8（非 RFC 4122 的草案档，且 v7 的时间有序性本库可用 Snowflake 直接表达）、`simpleUUID()` 去连字符（就是 `uuid.replace("-", "")`，写了就是转发层）、`fastUUID()`（非安全随机——要随机请显式喂 `env.rand` 或自己注入）。

## 4. ObjectId

hutool `lang/ObjectId.nextBytes()` 的实测布局是**三个大端 Int32**：`[4 字节秒级时间戳][4 字节 MACHINE][4 字节 计数器]`，共 12 字节 / 24 位十六进制。MACHINE 来自网卡列表哈希 ‖ PID ‖ ClassLoader 哈希（本库拿不到，见 0.2）⇒ 改成注入。

| 签名 | 读数（已冻结） | 边界/错误 | hutool 对位 | 差异声明 | 读数来源 |
|---|---|---|---|---|---|
| `object_id(timestamp_secs : Int64, machine : Int64, counter : Int64) -> String raise IdError` | `(1759552496L, 305419896L, 2596069104L)` → `68e0a3f0123456789abcdef0`；`(0L,0L,0L)` → `000000000000000000000000`；`(2038L, 4294967295L, 4294967295L)` → `000007f6ffffffffffffffff`；`(4294967396L, 1L, 2L)` → `000000640000000100000002` | `machine`/`counter` 不在 `0..0xFFFFFFFF` ⇒ `FieldOutOfRange` | `ObjectId.next()` | **只写低 32 位**（`(4294967396L)` 那档就是环绕成 `100`）——与 hutool 的 `bb.putInt((int) seconds)` 同行为，2038 之后照此环绕，不做"悄悄扩到 8 字节"的兼容破坏；输出恒小写；不提供 hutool 的 `withHyphen` 档（Mongo 规范就是 24 位无分隔） | `struct.pack(">III", …)` 现算 |

## 5. NanoId

hutool 的 NanoId **不是** npm `nanoid` 那份表序：它的默认表是 `_-0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ`（`_`、`-` 在前，数字、小写、大写在后）。表序直接决定读数，所以这条必须写死。

| 签名 | 读数（已冻结） | 边界/错误 | hutool 对位 | 差异声明 | 读数来源 |
|---|---|---|---|---|---|
| `nano_id_alphabet : String` | `_-0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ`（64 字符） | — | `DEFAULT_ALPHABET` | 与 npm `nanoid` 的 `A-Za-z0-9_-` **顺序不同**，跨栈互解必须选边 | hutool `lang/id/NanoId.java` 实测 |
| `nano_id_size : Int` = `21` | — | — | `DEFAULT_SIZE` | — | 同上 |
| `nano_id_bytes_needed(alphabet_len : Int, size : Int) -> Int raise IdError` | `mask = (2 << floor(log2(len-1))) - 1`、`step = ceil(1.6 * mask * size / len)`：`(64,21)`→34、`(64,10)`→16、`(3,8)`→13、`(2,1)`→1、`(1,5)`→8、`(100,24)`→49 | `len` 不在 1..255 或 `size <= 0` ⇒ `FieldOutOfRange`/`BadLength` | 私有 `mask`/`step` 计算 | 公开这条是为了让调用方能自己凑注入字节数（0.1 的推论）；`len == 1` 时 hutool 的 Java 式子退化（`(int) floor(log 0) == 0`）⇒ mask=1，本库照此定死并写进用例 | 逐条按同一公式现算 |
| `nano_id(alphabet : String, size : Int, rand : Bytes) -> String raise IdError` | 默认表 + 注入 `0x00..0x21`（34 字节）→ `_-0123456789abcdefghi`；默认表 + 21 个 `0xFF` → `ZZZZZZZZZZZZZZZZZZZZZ`；表 `"abc"` + 注入 `0x00..0x0B`、size=4 → `abca`（`0x03 & 3 == 3` 越表被丢，取下一个字节）；表 `"a"`、size=5 时 mask=1 ⇒ 奇数字节同样被拒，5 个字符要吃 9 字节（`0,1,0,1,0,1,0,1,0` → `aaaaa`） | 注入字节用完仍没凑够 ⇒ `EntropyTooShort`（携带 `nano_id_bytes_needed` 的应需数与实得数）；空表 / `size < 1` ⇒ `FieldOutOfRange`（携带被违反的下界 1） | `randomNanoId(random, alphabet, size)` | 表按**码点**索引（非 ASCII 表也能用）；拒绝采样与 hutool 逐字节同序 | Python 镜像同一算法逐条现算 |
| `nano_id_random(alphabet : String, size : Int) -> String raise IdError` / `nano_id_default() -> String raise IdError` | 走 `env.rand`，每轮取 `step` 个字节 | 取不到熵 ⇒ `NoEntropy` | `randomNanoId()` | 便捷版允许"再取一轮"（真实随机源不会耗尽）；纯函数版不许 | 见 §6 |

## 6. 时钟与熵的落点（零依赖四条在这一包怎么兑现）

| 入口 | 用的 OS 窗 | 档位实测 | 契约要求 |
|---|---|---|---|
| `Snowflake::next(now_millis)`、`ObjectIdGen::next(timestamp_secs)` | 不碰 | — | 时钟**必须**由调用方给；本包不提供"读现在几点"的发号入口 |
| `uuid_v4(rand)`、`nano_id(..., rand)` | 不碰 | — | 熵由调用方给 ⇒ 期望值可冻结 |
| `uuid_v4_random()`、`nano_id_random()`、`nano_id_default()` | `env.rand(n)` | 本机三档实测（同族结论见 `AGENTS.md`）：**wasm 有真熵**、**wasm-gc 拿不到熵**（`env.rand` 给 `None`）、native/Linux 由 CI 出证 | 拿不到就 `raise NoEntropy`。**绝不静默回落固定种子**——那会产出"看起来能用、实际可预测"的 ID，比直接失败坏得多 |

用例侧的时钟断言只做**单调下界**（`env.now()` 读数晚于某个已发生的真实时刻）与"同一次读数的往返恒等"，不写区间、不互比两次读数——那是计时依赖，慢机器上会假红（同 `date` 包 #2.10 的立场）。

## 7. 血统与来源汇总

| 格子 | 真上游 | 备注 |
|---|---|---|
| Snowflake 位分配 / TWEPOCH | Twitter snowflake 公开规格；hutool 与 MyBatis-Plus 各自照它实现 | 本库逐位对齐以保证跨栈同号 |
| UUID v3 / v4 / nil / namespace | **RFC 4122 §4.1–§4.4** | 期望值由 Python `uuid`（CPython 实现同一节）与手算 `hashlib` 双路互算 |
| `name_uuid` | JDK `java.util.UUID.nameUUIDFromBytes`（hutool 那侧是薄门面） | 本机 JDK 17 实跑取数；探针源码必须用 `\u` 转义写非 ASCII 输入，否则 `javac` 按 GBK 读 UTF-8 源文件会给出**看着权威其实脏**的读数（本轮实测：脏值 `607fee3e-…` vs 真值 `a7bac223-…`） |
| ObjectId 字节布局 | hutool `lang/ObjectId`（其设计源自 MongoDB ObjectId） | 布局实测是三个大端 Int32，与 Mongo 官方"4 秒 + 5 随机 + 3 计数器"的切法**不同**——本库照 hutool，因为要互解的是 Java 侧生成的值 |
| NanoId mask/step 与默认表 | hutool `lang/id/NanoId`（源自 `id` npm 包的某一版） | 表序与 npm `nanoid` 不同，已在 #5 写死 |
