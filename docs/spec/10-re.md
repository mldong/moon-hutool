# 10 · `re` —— 正则查询与替换（hutool `ReUtil` 对位·第一批）

> 状态：**契约已冻结**（10-05，实现未开工，本批 13 块是设计态红）。
> 号 = `docs/ROADMAP.md` 逐包表的行号（门禁 G13）。

对位文件：`hutool-core/src/main/java/cn/hutool/core/util/ReUtil.java`（987 行、52 个 `public static`），
常量表在 `cn/hutool/core/lang/RegexPool.java` + `PatternPool.java`（本批不动它们，见 §6）。
底座是 `moonbitlang/core` 的 `@string.Regex`——**本包不重新实现引擎**，所以这份契约的一半内容是
"引擎给不了的哪几件由本包补"，另一半是"引擎给得到的那些，本包不再包一层"。

## 0. 五条贯穿规则

| # | 规则 | 依据（都是实测，不是口味） |
|---|---|---|
| 0.1 | **不建全局模式池**：hutool 的 `PatternPool` 是进程级可变缓存表，本包要缓存由调用方持有 `compile` 的结果 | 与 `conv` 的"没有全局可变注册表"同一条立场（`docs/spec/09-conv.md` §0 第 2 条）；全局表会让"同一模式在两个调用点被换成两个实例"这种状态进契约 |
| 0.2 | **方言不假装**：本包不收 `\d`/`\w`/`\s`/`\xHH`/`\p{…}`/`\1`/`\A`/`\z`/`\Q`/`(?=…)`/`(?<=…)`/`*+`/全局 `(?i)`，也**不做自动改写** | 腿 B 实测：这些写法在 core 全部**编译期报错**（不是静默退化成字面量——那条推断被探针推翻了）；自动改写（`\d → [[:digit:]]`）会让同一串模式在两个引擎里读成不同东西，且改写规则本身就成了第二份方言 |
| 0.3 | **视图类型不外溢**：输入输出一律 `String`/`Array`；唯一例外是 `replace_by` 的回调参数 `MatchResult` | core 的 `String` 字面量不隐式转 `StringView`、`String` 也没有 `as_view`（`text` 包 §0 第 3 条同一条实测）；把视图塞进返回值会逼调用方处理两个串类型 |
| 0.4 | **位置口径 = UTF-16 码元**，与 Java `Matcher.start()/end()` 同档，不另发码位那一档 | 腿 B：`x` 于 `"😀x"` 的 `before().length()` = 2；腿 A 同名夹具 `firstidx` 也是 2。两腿同口径才敢只发一档 |
| 0.5 | **错误只带读数**：`BadPattern` 带模式串，`BadReference` 带那个引用原文 | core 的 `ParserError` **未导出**（`string/pkg.generated.mbti` 的 Errors 段是空的），位置与提示取不到；把它的文案抄进载荷 = 把 core 的措辞冻进本包契约 |

## 1. 边界：52 个方法怎么收成 24 条

腿 A 扫全 `ReUtil` 的方法名去重后是 18 个不同方法（其余 34 个是 `(String…)` 与 `(Pattern…)` 两份重载）。
本批的取舍：

| 面 | 进本批 | 不进，理由 |
|---|---|---|
| 判断 | `is_match` / `contains` / `count` / `is_valid_pattern` | — |
| 取组 | `find_first` / `find_first_group` / `find_first_named` / `groups_of_first` / `named_groups` / `group_names` | `getGroup0`/`getGroup1` 这类"把组号写进函数名"的便利档不收——本包用 `group : Int` 参数，组号写进名字是 hutool 为 Java 无可选参数发明的 |
| 批量 | `find_all` / `find_all_group` | `findAll(…, T collection)` 的集合注入档不收（MoonBit 有 `Array`，注入容器只增加出口形状） |
| 位置 | `first_position` / `last_position` | — |
| 删除 | `del_first` / `del_last` / `del_all` / `del_pre` | `replaceFirst` 单独不收：它就是 `replace_with_template` 的 `limit=1` 特例，而本包不暴露 `limit`（§5 第 10 行） |
| 替换 | `replace_with_template` / `extract_with_template` / `replace_by` | `extractMultiAndDelPre`（带 `Mutable` 游标那份）不收：本包没有 holder 类型，`del_pre` + `extract_with_template` 两步组合就是它的语义，组合可替代就别加一件 |
| 转义 | `quote` | `escape(char)` 单字档不收（`quote` 逐字应用同一张表）；`RE_KEYS` 那张表本身不导出 |
| 切分 | `split` | 对位**不是** `ReUtil`（那份 987 行里没有 split，实测扫描方法名清单）；本包量的是 JDK `String.split` 那一档，hutool 的 regex 切分不另立读数；不收 `limit` 参数（同 §5 第 10 行的理由） |
| 缓存 | `compile`（编译一次、复用由调用方决定） | `PatternPool.get` 的缓存语义不收（0.1） |
| 数字提取 | — | `getFirstNumber` 依赖 `PatternPool.NUMBERS`，随第二批常量表一起定 |
| 校验类 | — | `Validator.isEmail/isMobile` 那类是"码表 + 判定"，属第 11 行 `valid`，不在本包 |

**为什么每个函数都只收 `pattern : String`，不再发一份 `(Regex, …)` 重载**：hutool 的两份重载等于把
"要不要缓存"这个决定藏在每个入口后面。本包一轨（串），要复用就 `compile` 一次后直接用 core 的
`execute`/`find`/`split`/`replace_by`——那条路本来就是公开的，本包不再包一层壳。

## 2. 错误面

| 变体 | 载荷 | `raise` 点 |
|---|---|---|
| `ReError.BadPattern(String)` | 原模式串 | 所有 21 条收模式串的函数（编译这一关） |
| `ReError.BadReference(String)` | 模板里那个引用原文（如 `"$11"`） | `extract_with_template`、`replace_with_template` |

`is_valid_pattern` 是唯一吞掉错误的一件（判定的语义就是"能不能"，抛错反而要调用方 catch）。
`ReError` 不进 `conv` 的 `ConvError`：两包错误面不共用，见 `docs/spec/09-conv.md` §2。

## 4. 两条腿与统计（读数来源）

1. **腿 A · 参照实现**：真 `hutool-core-5.8.35.jar`（Maven Central 取）+ 本机 JDK 17.0.14 跑 `ReUtil`，
   夹具 = 24 个模式 × 判断/取组/批量/位置/模板/删除/切分/转义/回调，共 **859 条**；
   第二轮专补三件难料：12 组模式的模板降序（16 条）、零宽量词的 `count`/`find`/`del_all`/`find_all`（36 条）、未参与组与折叠的 Unicode 档（6 条），合计 **917 条**（两份读数文件 `wc -l` = 859 + 58）。第三轮补两档契约没冻到的：模板引用了"存在但没参与"的组、`is_match` 在 `a|ab` 上的择路整串档（`ReRef3.java` 6 条，`wc -l` 现读）⇒ 腿 A 合计 **923 条**。
   **另有一腿 A′**：`Pattern`/`Matcher` 直跑 6 条（`JdkUnmatched.java`），只在"参照实现自己崩了"的那些档当引擎侧对读——
   实测 `replaceAll("[$1]")` 于 `(a)?b` 的 `"b"` 给 `[]`、`appendReplacement` 于 `"xb"` 给 `x[]`、`replaceAll("<$1|$2>")` 于 `(a)(b)?c` 的 `"ac"` 给 `<a|>` ⇒ **未参与组代入空串**（§5 第 12 行）。同一轮还取了 `ReUtil.isMatch("a|ab","ab")` = `true`（腿 A）——
   `is_match` 的语义是"整串被匹配"而**不是**"最左那一段恰好占满整串"，这条是实现级判别夹具（`re_test.mbt` 第 13 块）。
   命名组枚举那一条腿在 JDK 17 默认模块封锁下直接
   `InaccessibleObjectException`，加 `--add-opens java.base/java.util.regex=ALL-UNNAMED` 才跑出 `[a, b]`。
2. **腿 B · 运行时引擎**：`@string.Regex` 探针（编译面 45 条 + 组/命名/择路/锚点/DOTALL/POSIX 档/索引/
   `find`/`split`/`replace_by` 的 `limit` 语义/`\b` 与 CJK 相邻），共 **114 条**，
   跑在 `wasm`、`js`、`wasm-gc` 三档，**三份输出逐字节相同**（`diff` 空）——这条是本包敢于承诺
   跨档一致的全部依据（引擎是纯 MoonBit 的 Brzozowski 导数自动机，`js` 档不借宿主 `RegExp`：
   全链路 46 个非测试文件里 `extern`/`%if js`/`@gen` 零命中，实测扫描）。
3. **两腿对撞**：同名夹具逐条比。一致的直接进期望值（`count`/`first_position`/`split` 的三段空档/
   `del_*` 五族/模板 `$1-$2`/降序 `$1-$11`/零宽迭代数）；不一致的**全部**进 §5，共 12 行，每行带两侧读数。
4. **推翻的一条推断**：调研阶段（读 core 的 parser 源码）得出"`\1`/`\p{L}`/`\A` 不在转义集里，
   会退化成匹配字面反斜杠"——**探针实测是编译期报错**。源码读出来的"会走到哪一支"不等于"实际行为"，
   这条改判同时删掉了"本包必须自己预检否则静默错"的立项理由，剩下的 `BadPattern` 只是把 core 的
   异常换成带模式串的读数。
5. **第二批的前置普查（扫源码，不是对撞）**：把上游 `RegexPool.java`/`PatternPool.java` 两份源码逐条扫
   字面量——注释掉的常量先剔，`String NAME = "…" + "…"` 按引号配对取全串（EMAIL 那两条里有转义引号，
   简单正则会在第一个 `\"` 处截断，这条普查就是这么翻过一次的），再按 §5 第 1 行的禁集逐条查。
   读数 **34 / 24 / 10** 与逐条清单在临时候跑件里，第二批开工时随那一笔补进本节。

## 5. 不跟随清单

| # | 分岔 | 腿 A 实测 | 本包 | 理由 |
|---|---|---|---|---|
| 1 | `\d` `\w` `\s` `\xHH` `\p{…}` `\1` `\A` `\z` `\Q` `(?=…)` `(?<=…)` `*+` `(?i)`（全局） | 全部合法（如 `\d+` OK、`\1` OK） | 一律 `BadPattern`：本包不收、也不自动改写 | 腿 B 实测这些写法编译期报错（0.2）；自动改写会让同一串模式在两个引擎里读成不同东西 |
| 2 | `[:ascii:]`（POSIX 裸写，不在方括号里） | 合法（当普通字符类） | `BadPattern` | 腿 B 报错；这不是"少支持"而是同一串在两处语义不同，收进来会掩盖调用方写错 |
| 3 | `is_match("", "abc")` | `true`（`StrUtil.isEmpty(regex)` 那条短路） | `false` | 参照实现自己的哨兵与它底下的引擎相反（JDK `matches()` 在此是 `false`）；空模式只匹配空串是可解释的唯一答案 |
| 4 | 取组时组号越界 / 名字不存在 | `IndexOutOfBoundsException: No group 9` / `IllegalArgumentException: No group with name <z>` | `None` | 查询类只留一个出口档（与 `conv` 的 `Option` 立场一致）；把参照实现的崩当契约不成立 |
| 5 | 模板引用不存在的组 | `IndexOutOfBoundsException: No group 9`（`$9`/`$10`/`$11`/`$111` 全崩） | `BadReference("$N")` | 同第 4 行的判断，但模板是**构造**不是查询：写错的引用必须报，不能静默留 `$9` 在输出里 |
| 6 | 切分的空段修剪 | 尾随空段被丢：`[,;]` 于 `",a,"` ⇒ `["", "a"]`；空模式于 `"abc"` ⇒ `["a","b","c"]`（首部空段也不吐） | 跟引擎：`["", "a", ""]` 与 `["", "a", "b"]` | 腿 B 实测两条都保留空段。本包的切分出口就是 core 的 `split`——再叠一层"修剪"等于在引擎之上造第二份语义；参照实现那侧的修剪本来就是 `String.split` 的历史包袱。**这条是交叉核对抓出来的**：写契约时我以为"尾随空段两腿一致"，腿 B 的读数直接推翻 |
| 7 | `MULTILINE`（`(?m)` / `Pattern.MULTILINE`） | 合法，`^`/`$` 按行 | 无对应档：`^`/`$` 恒整串（实测 `^b` 于 `"a\nb"` 不命中） | 腿 B 没有行级锚点；要逐行由调用方先切行再匹配，本包不发明"假装 multiline"的前缀处理 |
| 8 | 大小写折叠的写法 | 全局 `(?i)` 可用；对 `É`/`é`、`I`/`ı` 也是 `false`（ASCII 档，两腿一致） | 只收 scoped `(?i:…)`；非 scoped 的 `(?i)abc` ⇒ `BadPattern` | 折叠**范围**两腿实测同为 ASCII 档（不构成差异），差异只在写法（第 1 行） |
| 9 | 命名组的来源与顺序 | 反射 `Pattern.namedGroups()`，是 `HashMap`（键序不可依赖），且在 JDK 17 默认配置下整条腿 `InaccessibleObjectException` | 扫模式串，**声明序** | 参照实现那两份证据都在（实测）；依赖反射的结果既不稳定也不是本包能引的东西（零依赖 + 无反射） |
| 10 | `replace_by` 的 `limit` | hutool 无 limit 概念；core 有，但实测 `limit=-1`/`-2`/`0` 都**一处都不换**（省略参数才是全部） | 本包不暴露 `limit`，回调一律全量 | 把 `-1` 当"无限"是别的语言的直觉；core 的负数档是陷阱，透传等于把陷阱写进我们的契约。要"只换第一处"用 `del_first`/`replace_with_template` 的语义另议 |
| 11 | 命名组映射里"名字在、这组没参与" | `getAllGroupNames` 的 Map 值位进的是 `null`（同族夹具实测 `[b, null]`） | 该键不出现（出口是 `Map[String, String]`，不做 `String?` 值位） | 一个值位同时装"有名字没值"与"根本没这个键"是要调用方猜；两个含义分开放才可用。双 `Option`（`Map[String, String?]` 的 `.get` 返回 `String??`）在 MoonBit 里也不可读 |
| 12 | 模板引用了"存在但没参与"的组 | `extractMulti("(a)?b","b","[$1]")` 与 `replaceAll` 同档直接 `NullPointerException: Cannot invoke "java.lang.CharSequence.toString()" because "replacement" is null`（实测）；腿 A′ 的 JDK `Matcher` 在同一夹具上给 `[]` / `x[]` / `<a|>` | 代入**空串** | 参照实现在这一档是崩、不是语义；崩底下那一层（`Matcher` 的替换语义）读数就是空串，本包取它。与第 4/5 行同一条立场：不把内部异常当契约 |

## 7. 引擎裁决与改写表（给调用方看的，不是本包的义务）

腿 B 实测的编译面（45 条那一组），一张表说清"能写什么"（**本包不收的写法一律 `BadPattern`，不做自动改写**，
下表只是"调用方自己要改写成什么"的对照）：

| Java 写法 | core | 等价改写 |
|---|---|---|
| `\d` `\w` `\s` 及大写取反 | 编译报错 | `[[:digit:]]`/`[[:word:]]`/`[[:space:]]`（实测两腿同为 **ASCII 档**：`\w@中` 与 `[[:word:]]@中` 两腿都不命中；`[[:word:]]` 含 `_` 与数字） |
| `\xHH` | 编译报错 | 码位写法 `\u00HH`（实测 `\u0041` OK） |
| `\p{L}` 等 Unicode 块类 | 编译报错 | 无等价物；块类不在零依赖范围（码表独立成数据件的立场同 `num`） |
| `\1` 反向引用、`(?=…)`/`(?<=…)`、`*+` | 编译报错（**不是**静默退化——源码读出的推断被探针推翻） | 无等价物，功能整档不做 |
| `(?i)abc` 全局折叠 | 编译报错 | scoped `(?i:abc)`（实测折叠只对 ASCII 成立：`(?i:é)` 不匹配 `É`） |
| `Pattern.MULTILINE` / `(?m)` | 无此档 | `^`/`$` 恒整串；逐行需先切行 |
| `Pattern.DOTALL` | **默认就是 DOTALL** | 什么都不用做（实测 `.` 命中 `\n`），这也是 hutool 全线带 DOTALL 的那条默认在本包同档 |
| `(?'name'…)`、`(?P<name>…)` | 编译报错 | 只认 `(?<name>…)`（实测 Java 也只认这一种，两腿同档） |
| `a{2,1}`、`a{300}`、`[a-]`、`[-a]`、`[[:alpha:]` | 编译报错 | 其中量化上界是 core 的硬限制（实测 `a{256}` 合法、`a{300}` 报错） |
